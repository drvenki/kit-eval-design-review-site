Statistics

Recommendation

One model, four sensitivity analyses, and a decision about the EVO cfDNA run that has to be made before any of the rest matters.

Primary analysis

For each sample type separately, on the logit of the conversion rate:

m <- lmerTest::lmer(logit(y) ~ kit + (1 | kit:batch), data = d, REML = TRUE)
anova(m, ddf = "Kenward-Roger")          # omnibus

with pairwise kit contrasts computed on the batch means using the model's pooled batch-level SD, Holm-adjusted within sample type. Implemented in program/plot_conversion_rate_batchlevel_20260817.R.

Why this rather than a rank test on batch means

  • It honours the aggregation ST asked for. For this balanced design the mixed model is algebraically the same test as an ANOVA on the three batch means; the technical replicates contribute only through the within-batch variance, which is exactly their role. Verified on your data: cfDNA ANOVA-on-batch-means F(5,12) = 8.70 versus LMM F(5,12.0) = 8.73.
  • It recovers the power that naive aggregation throws away, by pooling batch-to-batch variance across the five or six kits within a sample type. Error df go from 4 to 10 or 12. That is the entire difference between 0/15 and 6/15 in cfDNA.
  • It reports the batch effect instead of assuming it away. The variance components go in the figure subtitle and in Table 1. A reviewer who asks "did you check for batch effects?" is answered by the figure itself.
  • It does not require independence of the technical replicates. That is precisely what the random intercept models.

Report per sample type: F, numerator and denominator df, p; between-batch SD, within-batch SD and ICC; and per kit the mean of the batch means with its SD and n (3 batches, 8 or 9 libraries).

"How can we perform a similar test as already done?"

The presentation stays the same: four panels, a boxplot per kit, points overlaid, significance brackets. Three things change.

Change 1 — the overlaid points become the 3 batch means

"Three points become one point", as requested. Keep the 9 libraries as small grey dots behind them so the reader can see the technical spread, and label them in the legend as technical replicates so nobody mistakes them for the analysis unit. If you prefer to follow ST literally, drop the grey dots; the inference is unchanged either way.

Change 2 — batch colour is retained, but its meaning changes

It is no longer "here are 9 points coloured by a nuisance factor", which is ST's objection, but "here are the 3 experimental units". That is a legitimate and informative use of colour. Dropping the colours entirely is also fine.

Change 3 — the subtitle carries the LMM statistics

Instead of the Kruskal–Wallis line. If you want to keep ggbetweenstats for the aesthetics, call it with results.subtitle = FALSE on the batch means and supply your own subtitle. The standalone script is simpler and avoids the p.adjust.method inconsistency described below.

The EVO cfDNA run: decided

Resolved, 17 Aug 2026: use the first run

The January/February 2025 preparation is the one that goes into the paper. The June 2025 re-prep is excluded because it was carried out with documented protocol errors by the laboratory personnel, so it is a failed preparation rather than a competing estimate.

This matches what the analysis scripts were already doing, so no figure or number on this site changes: cfDNA omnibus F = 8.73, p = 0.0011, with 6 of 15 contrasts surviving Holm, and EVO at 0.421. The script default EVO_CFDNA_RUN <- "orig" is correct as it stands.

What does change is that the choice is now a documented decision with a stated reason rather than an unexplained grepl(). That was the substantive problem. See what still needs recording below.

The background, for the record. Collected prep info.xlsx marks the January/February 2025 EVO cfDNA libraries EVO-FIRST-RUN, status "Will be re-prepped/re-captured", and records a full re-prep in June 2025 (dev250624, dev250626.1/.2, capture pool tga250701). The plotting scripts filter !grepl("EVO.*-KH20250815"), that is, they keep the first run and discard the re-prep. Read from the spreadsheet alone this looked like an oversight, because the sheet records an intention to re-prep and says nothing about how the re-prep turned out. With the laboratory history added, the filter is correct: the re-prep failed, so the first run is the only valid EVO cfDNA data.

EVO cfDNA run usedEVO batch meansEVO mean (SD of batch means)cfDNA omnibus
First run (currently used)0.387 / 0.462 / 0.4150.421 (0.038)F = 8.73, p = 0.0011

The table shows why this mattered enough to settle explicitly. The re-prep's wild batch spread (0.248 against 0.611 and 0.600) inflates the pooled error term roughly five-fold, which is what drags the whole cfDNA panel from p = 0.001 to p = 0.076. Had the re-prep been a valid preparation, that spread would have been a real finding about EVO's stability at 30 ng and the paper would have had to report it. Since the spread is a consequence of the protocol errors, it is measurement failure, not kit behaviour, and including it would have been actively misleading.

What still needs recording

"Prepped with mistakes" has to become specific

The justification is sound but it currently exists only as spoken lab knowledge, and nothing in the repository records it. A reviewer, or you in three years, will see nine EVO libraries silently absent. Three things to do:

  1. Write down what went wrong, concretely: which step, which batches, who identified it and when. One or two sentences in documentation/ and in the prep sheet's status column, not just in someone's memory.
  2. Update the prep sheet. It currently labels the January/February run EVO-FIRST-RUN with status "Will be re-prepped/re-captured", which now reads backwards. The June rows need a status marking them as failed and excluded.
  3. Say it in the Methods rather than leaving a bare grepl() as the only trace. Suggested wording: "EVO cfDNA libraries were re-prepared in June 2025; that preparation was excluded from analysis because of documented protocol deviations during library preparation, and the January to February 2025 preparation was used."

Do not present the re-prep as a sensitivity analysis in the supplement. A failed preparation is not an alternative estimate, and showing it alongside would invite exactly the wrong interpretation. Excluding it with a stated reason is the honest treatment.

The script default is already correct (EVO_CFDNA_RUN <- "orig" in program/plot_conversion_rate_batchlevel_20260817.R), so nothing needs re-running. Add a comment there pointing at the documented reason so the next person does not have to ask.
